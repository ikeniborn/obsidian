# TURN/STUN & P2P

WebRTC NAT-traversal infrastructure for the ServerPeer backend's peer-to-peer sync. A public STUN server discovers external addresses, a local coturn TURN server relays traffic when direct P2P fails, and a local Nostr relay carries WebRTC signaling. This stack is part of the **LEGACY/FROZEN** [[serverpeer-backend#Legacy Status]] backend — production runs CouchDB. Firewall ports are handled in [[firewall-security#UFW Configuration]].

## TURN/STUN Purpose

TURN/STUN enables WebRTC P2P connections between Obsidian clients and ServerPeer when both sit behind NAT. STUN discovers a peer's public address; TURN relays packets as a last resort. Used only by ServerPeer ([[serverpeer-backend#Legacy Status]]) — CouchDB sync needs none of this.

The components, per `scripts/coturn-setup.sh` and CLAUDE.md:
- **STUN** — Google public server `stun:stun.l.google.com:19302`. Stateless; lets a client behind NAT learn its own external IP/port.
- **TURN** — local coturn on the VPS (`turn:<external-ip>:3478`). Relays media/data when direct P2P is impossible (symmetric NAT, restrictive firewalls).
- **Signaling** — local Nostr relay (`nostr-rs-relay`) exchanges WebRTC offers/answers; it carries signaling only, not sync data.

Because Obsidian clients are typically behind home/corporate NAT and ServerPeer has a public IP, a TURN fallback is required to guarantee connectivity. The associated firewall rules (`3478/udp`, `3478/tcp`, `49152:65535/udp`) are opened in [[firewall-security#UFW Configuration]].

## Coturn Configuration

`scripts/coturn-setup.sh` generates `/etc/turnserver.conf` from `/opt/notes/.env`, enables the service in `/etc/default/coturn`, and restarts it. It must run as root, requires coturn installed (via `install.sh`) and `.env` configured (via [[setup#TURN Configuration]]).

`generate_coturn_config()` (coturn-setup.sh:99) writes a config marked "DO NOT EDIT MANUALLY" with:
- `listening-ip=0.0.0.0`, `external-ip=${COTURN_EXTERNAL_IP}` (the VPS public IP).
- `listening-port=${COTURN_LISTENING_PORT:-3478}`; relay range `min-port=49152` / `max-port=65535`.
- `realm=${TURN_REALM}`, `lt-cred-mech` (long-term credentials), `user=${TURN_USERNAME}:${TURN_PASSWORD}`.
- `no-tls`, `no-dtls`, `no-tcp-relay` (UDP relay only), `fingerprint` (required for WebRTC), `verbose` logging to `/var/log/turnserver.log`.

**Peer-IP allow/deny lists** prevent the relay from being abused as an open proxy:
- `allowed-peer-ip=127.0.0.1` always; if a `notes-serverpeer` container is running, the script auto-detects its Docker subnet (line 104) and adds `allowed-peer-ip=<subnet>` for P2P relay.
- `denied-peer-ip` blocks `10.0.0.0/8`, `192.168.0.0/16`, and the `172.16-17` / `172.19-31` ranges (excluding the project's own Docker network). The script explicitly avoids a blanket `0.0.0.0-255.255.255.255` deny, which would block everything.

`enable_coturn_service()` (line 188) flips `TURNSERVER_ENABLED=1` in `/etc/default/coturn`; `restart_coturn()` (line 201) runs `daemon-reload` + `systemctl restart coturn` and aborts if the service does not come up.

## Credential Generation

coturn credentials are **not** generated here — they are produced by `setup.sh` and stored in `/opt/notes/.env`. `coturn-setup.sh` only consumes them; it errors out if they are missing. See [[setup#TURN Configuration]].

`load_env_file()` (coturn-setup.sh:78) sources `.env` and validates the required variables, failing fast if absent:
- `TURN_USERNAME` (default `obsidian`) and `TURN_PASSWORD` (32-char hex generated by `setup.sh`).
- `COTURN_EXTERNAL_IP` (server public IP, detected via `curl ifconfig.me` in setup).
- `TURN_REALM`, `COTURN_LISTENING_PORT` (consumed with a `3478` default).

These same values feed the derived `SERVERPEER_STUN_SERVERS` / `SERVERPEER_TURN_SERVERS` entries used by the ServerPeer container and the Obsidian client. `display_summary()` (line 215) echoes the connection details (STUN, TURN URL, username, password) for client configuration; `.env` itself is chmod 600.

## Nostr Relay Signaling

A local `nostr-rs-relay` container provides the WebRTC signaling channel (offer/answer/ICE exchange) for ServerPeer P2P. It transports signaling only — actual note data flows directly between peers or via the TURN relay, never through Nostr. Defined in `docker-compose.nostr-relay.yml`.

From `docker-compose.nostr-relay.yml`:
- Image `scsibug/nostr-rs-relay:latest`, container `${NOSTR_RELAY_CONTAINER_NAME:-notes-nostr-relay}`, `restart: unless-stopped`.
- Bound to `127.0.0.1:${NOSTR_RELAY_PORT:-7000}:7000` — localhost only; external clients reach it through nginx as `wss://<domain>/serverpeer/` (see [[nginx-proxy#ServerPeer Template]]).
- Volumes: `${NOSTR_RELAY_DATA_DIR:-/opt/notes/nostr-relay-data}:/data` and a read-only `./nostr-relay/config.toml`.
- Joins `notes-network`, whose external/name attributes follow `NETWORK_MODE` in `.env` (shared/isolated/custom) — see [[architecture#Network Architecture]].
- Healthcheck is disabled (the minimal image lacks diagnostic tools); health is inferred from logs. Resource limits: 0.5 CPU / 512M (limit), 0.1 CPU / 128M (reservation).

This local-relay approach is the recommended default (lowest latency, best privacy); an external relay (e.g. `wss://exp-relay.vrtmrz.net/`) is a higher-latency alternative.

## NAT Traversal Flow

The connection sequence is STUN → direct P2P → TURN fallback. A client first discovers its public address via STUN, exchanges that candidate through the Nostr signaling relay, attempts a direct WebRTC connection, and only relays through coturn if the direct path fails. Ports for each stage are governed by [[firewall-security#UFW Configuration]].

Per the architecture in CLAUDE.md:
1. **STUN query** — client behind NAT asks Google STUN for its external IP/port.
2. **Signaling** — WebRTC offer/answer is relayed via the local Nostr relay.
3. **Direct P2P attempt** — peers try a direct WebRTC connection using gathered ICE candidates.
4. **TURN fallback** — if the direct attempt fails (symmetric NAT / strict firewall), coturn relays traffic between client and ServerPeer.

Trade-off: the TURN fallback guarantees connectivity but adds latency, since all traffic then transits the VPS. High latency in practice means the direct P2P path failed and traffic is being relayed — expected behavior for restrictive NAT. Backend selection that enables this entire path is documented in [[setup#Backend Selection]] and deployed via [[deployment#Backend Deployment]]; remember the whole ServerPeer/P2P feature is [[serverpeer-backend#Legacy Status]].
